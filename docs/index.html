Technical Challenges

핵심 기술 도전 4가지

① Depth 센서 없이 3D 좌표 복원 — Ray-Plane Intersection

단안 카메라 픽셀 하나는 카메라에서 뻗어나가는 무한한 Ray 위의 어느 점이든 될 수 있습니다. "상자는 항상 Z_surface 위에 있다"는 물리적 제약 하나가 해를 유일하게 만듭니다.

# core/coord_transform.py
ray_c  = K_inv @ [cx, cy, 1.0]      # 카메라 좌표계 Ray
ray_b  = R @ ray_c                   # Base 좌표계로 회전
t = (z_surface - origin[2]) / ray_b[2]  # 교점 파라미터
P = origin + t * ray_b               # 파지 좌표 (mm)

결과: 파지 좌표 오차 <0.95 mm (verify.py Step B 실측)

트레이드오프: 물체가 평면 위에 있을 때만 동작. 신발 상자는 항상 트레이 위에 놓이므로 도메인에서 보장.

② Hand-Eye 캘리브레이션 — AX = XB (Tsai-Lenz)

카메라가 로봇 EE에 고정 마운트되어 있어, Flange → Camera 변환 행렬 T_flange2cam을 실측해야 좌표 변환이 가능합니다.

# N개 자세에서 수집
A_i = T_base2flange   # 관절 각도로 계산
B_i = T_cam2board     # 체커보드 solvePnP

# Tsai-Lenz 풀이
T_flange2cam = cv2.calibrateHandEye(TSAI)

왜 Flange 기준인가: TCP는 그리퍼에 따라 달라지는 가변값. Flange는 공구 교체와 무관한 고정점이므로 T_flange2cam은 그리퍼 교체 후에도 재수행 불필요.

수집 전략: observe 자세 근방 ±30~50mm / ±15° 소변위 25포즈 집중 수집

결과: 캘리브레이션 잔차 1.245 mm

③ 이동 중 프레임 배제 — 순차 실행으로 타이밍 보장

로봇 이동 중 캡처된 OBB 검출 결과를 사용하면 오파지 발생. move_to()가 완전히 반환된 이후에만 wait_for_detection()이 호출되도록 순차 실행으로 보장.

# nodes/vision_pick_place_node.py
self._motion.move_to(observe_pose)          # blocking — 완전 정지 대기
flange = self._motion.get_flange_coords()  # Flange 좌표 읽기
self._transformer.update_pose(flange)      # T_base2cam 재계산
obb = self._detector.wait_for_detection(timeout=10.0)  # 정지 후 첫 프레임

④ 로봇 없이 알고리즘 검증 — Clean Architecture (v1 → v2)

v1에서는 좌표 변환 코드가 ROS2 노드에 묶여 있어 수학 로직 하나를 수정할 때마다 로봇 연결 + ROS2 부팅이 필요했습니다. v2에서 Core/Node를 분리했습니다.

① CLAHE

LAB L채널에 적용. 색 정보(A, B)는 유지한 채 밝기만 정규화 → 조명 변화에도 HSV 범위 안정적 유지

② HSV 마스킹

흰색 상자 HSV 범위로 inRange. Morphology(CLOSE+OPEN)로 노이즈 제거 및 구멍 메움

③ minAreaRect

최대 면적 윤곽선에서 최소 면적 회전 직사각형 추출. cx, cy, w, h, θ 획득

HIL Troubleshooting

체계적 오차 해결 2건

통합 테스트에서 발견된 오차를 격리 스크립트로 원인을 확정했습니다.

Z축 +110 mm → 0 mm
증상
로봇이 상자보다 정확히 110 mm 높은 공중을 파지 시도
원인
z_surface 측정 시 그리퍼 tip이 상자에 닿은 상태에서 Flange 좌표를 읽음. Flange는 tip보다 그리퍼 길이(110 mm)만큼 위에 있으므로 z_surface 과대 측정
보정
1차: 측정값에서 그리퍼 길이 수동 차감
개선: set_end_type(1)로 TCP 좌표 직접 읽기
Y축 +16.3 mm → <0.95 mm
증상
X축은 정확한데 Y 방향으로만 일정하게 16.3 mm 편향
원인
verify.py Step B로 알려진 위치에서 16.3 mm 재현 확인. 캘리브 bias + 카메라 브래킷 조립 공차 누적 추정
보정
반복 측정에서 편향이 안정적으로 재현됨을 확인 → pick_offset_mm: [0, -16.3, 0] 정적 보정

향후 개선 방향

01
C++ 포팅

최대 384.6 ms 편차의 주요 원인은 Python GIL. core/를 Eigen + OpenCV C++로 재작성하면 20 ms 이내 예상. Clean Architecture 덕분에 core/만 교체하면 됩니다.

02
Visual Servoing

현재 개루프(Open-loop) 제어. observe 자세에서 한 번 계산 후 이동. 폐루프 카메라 피드백으로 외부 섭동 대응 가능.

03
ROS2 Lifecycle Node

현재 게이팅은 순차 코드 흐름에 의존. ROS2 표준 상태 머신으로 노드 재시작 시 안전한 초기화 확보.
